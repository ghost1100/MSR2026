\begin{abstract}
We attempted to analyze testing behavior across AI coding agents using 932,791 pull requests from the AIDev dataset, but discovered fundamental validity issues that completely invalidate the analysis. Critical failures include: (1) demonstrably unreliable agent attribution (e.g., GitHub Copilot showing only 379 users), (2) statistical test violations due to clustered observations, (3) systematically biased test detection methodology, and (4) impossible results indicating data corruption (OpenAI Codex: 98.5\% test rates). Rather than hide these issues, we present this as a methodological cautionary tale for the software engineering research community. The analysis demonstrates how large-scale observational studies can produce misleading results when fundamental assumptions are violated, regardless of sample size or apparent statistical rigor.
\end{abstract}

\begin{IEEEkeywords}
artificial intelligence, software testing, empirical software engineering, code generation, pull requests, AI-assisted development
\end{IEEEkeywords}

\section{Introduction: A Failed Research Attempt}

We initially set out to analyze AI coding agent behavior using the AIDev dataset, focusing on testing practices across different agents. However, our investigation revealed fundamental validity issues that render this approach completely invalid and serve as an important methodological warning for the software engineering research community.

\subsection{Why This Analysis Failed}

Our analysis failed due to multiple, compounding validity violations:

\textbf{Agent Attribution Failure:} The dataset's agent labels are demonstrably unreliable. GitHub Copilot appears with only 379 users despite having millions of actual users, while lesser-known tools show tens of thousands. This attribution failure destroys all internal validity.

\textbf{Statistical Assumption Violations:} Pull requests from the same repository and user are not independent observations, violating the fundamental assumptions of chi-square tests and rendering all statistical inference meaningless.

\textbf{Impossible Results:} OpenAI Codex allegedly produces 98.5\% test-including PRs across 61,653 users—a result so implausible it indicates severe data corruption or systematic bias.

\subsection{The Value of Reporting Failures}

Rather than abandon this work, we present it as a cautionary tale about how superficially rigorous analyses can mask fundamental validity failures. The software engineering research community needs transparent reporting of methodological failures to improve future research practices.

Consider the implications: if AI agents are associated with systematically different testing behaviors, understanding these patterns could inform evidence-based tool selection and workflow design. However, establishing whether agents cause these differences or whether developers select agents based on project needs requires controlled studies beyond observational data. Our study documents associations between agent choice and testing patterns, providing a foundation for future causal research.

\subsection{Research Scope and Approach}

This study addresses these questions through analysis of the AIDev dataset containing 932,791 pull requests where AI agents were identified as contributors. This large-scale observational study complements existing controlled experiments and small-sample studies by documenting testing behavior patterns across diverse real-world contexts.
\par\noindent\textbf{Upfront caveats.} \emph{Devin} appears as a single detected user and is excluded from aggregate summaries unless explicitly stated. \emph{OpenAI Codex} labeling likely overlaps with Copilot-era usage during 2021--2023; we treat Codex labels as proxies and include sensitivity checks (exclude Codex; reassign Codex to Copilot).
\par\noindent\textbf{Temporal note.} The dataset spans roughly 2021--2023. Public Codex API access ended in March 2023; observed patterns partly reflect that period. Results describe associations in this timeframe and may not generalize to later model versions.

We observe substantial testing rate variation: OpenAI Codex shows 98.5\% test inclusion while Cursor shows 18.7\%. While these patterns are statistically significant (p < 0.001, Cramér's V = 0.646), establishing whether they reflect agent capabilities, user selection, or other factors requires future controlled studies.

This study's primary contribution is methodological: demonstrating why observational analysis of AI tool behavior is fundamentally unreliable without proper experimental controls. Specific limitations identified include:

\begin{itemize}
    \item \textbf{Agent attribution uncertainty}: Labels based on unreliable metadata make group comparisons meaningless
    \item \textbf{Statistical test violations}: Clustering in data invalidates standard significance tests
    \item \textbf{Measurement artifacts}: Keyword-based test detection introduces systematic error
    \item \textbf{Severe confounding}: Selection effects likely explain observed patterns
\end{itemize}

These findings demonstrate that reliable inference about AI tool behavior requires controlled experimental designs with verified agent attribution, not observational analysis of convenience datasets.

\subsection{Research Questions}

We address four research questions using the complete dataset of 932,791 pull requests, emphasizing measurement and association rather than causal claims:

Given the fundamental validity limitations identified in this dataset, we reframe our research questions:

\textbf{RQ1: What methodological challenges prevent valid inference about AI agent behavior from observational data?} We identify specific threats including label unreliability, statistical assumption violations, and confounding.

\textbf{RQ2: To what extent do measurement artifacts and selection effects explain observed patterns?} We examine how dataset characteristics may generate spurious associations.

\textbf{RQ3: What experimental design requirements are necessary for valid AI tool comparisons?} We specify conditions needed for reliable causal inference about agent behavior.

These RQs focus on measurement and description rather than causal inference, appropriate for observational data without experimental controls.

\subsection{Key Contributions}

This paper makes several contributions to empirical AI-assisted software engineering:
\begin{enumerate}
    \item \textbf{Large-scale measurement}: Analysis of testing behavior across 932,791 PRs from the complete available dataset
    \item \textbf{Quantification of variation}: Documentation of substantial testing rate differences (18.7\% to 98.5\%) with large effect size (Cram\u00e9r's V = 0.646)
    \item \textbf{Methodological transparency}: Explicit treatment of confounders, measurement limitations, and threats to causal inference in observational AI tool research
    \item \textbf{Practical implications}: Evidence-informed considerations for AI tool evaluation and selection
    \item \textbf{Research agenda}: Identification of key questions requiring controlled experimentation to establish causality
\end{enumerate}

\section{Methodology}

\subsection{Dataset Provenance and Comprehensive Coverage}

\textbf{Data Source}: This study analyzes the AIDev dataset \cite{li2024rise}, publicly available on HuggingFace (\texttt{hao-li/AIDev}, configuration: \texttt{all\_pull\_request}). The dataset comprises 932,791 pull requests from GitHub repositories where AI coding agents were detected as contributors through repository metadata, commit messages, and user declarations. The dataset was collected as part of research into AI-assisted software development practices and made publicly available for the MSR community.

\textbf{Dataset Schema}: Each pull request record contains:
\begin{itemize}
    \item \texttt{agent}: Categorical variable identifying the AI tool (OpenAI Codex, GitHub Copilot, Cursor, Devin, Claude Code)
    \item \texttt{user}: GitHub username of the PR author (string)
    \item \texttt{title}: PR title text (string, may be null)
    \item \texttt{body}: PR description/body text (string, may be null)
    \item \texttt{state}: PR status (categorical: open, closed, merged)
    \item \texttt{files}: File paths modified in the PR (list)
    \item Metadata: Repository identifiers, timestamps, labels
\end{itemize}

\textbf{Agent Attribution Methodology and Limitations}: The \texttt{agent} field is derived from multiple signals in the original data collection:
\begin{enumerate}
    \item Self-reported agent usage in commit messages or PR descriptions (e.g., ``Generated with GitHub Copilot'')
    \item Repository metadata indicating AI tool integration
    \item User profile information declaring AI tool usage
    \item Heuristic patterns in code changes characteristic of specific tools
\end{enumerate}

\textit{Critical Limitation}: We do not have access to the exact attribution algorithm used in the original dataset collection. This introduces potential classification noise—some PRs may be misattributed, and human-edited AI contributions cannot be distinguished from pure AI output. Agent labels should be interpreted as ``PRs where agent X was likely involved'' rather than ``PRs written entirely by agent X.'' This measurement error would tend to attenuate observed differences, making our findings conservative estimates.

	extbf{OpenAI Codex Timeline Clarification}: OpenAI Codex powers multiple tools including GitHub Copilot, and ``Codex'' in this dataset likely refers to direct API usage and Copilot-era contributions labeled as Codex during collection. Public Codex API access ended in March 2023; our sensitivity checks (exclude/reassign Codex) probe this labeling ambiguity.

\textbf{Population-Level Analysis}: Unlike previous studies constrained by computational or access limitations, we process the complete publicly available dataset (754MB, 932,791 records). This eliminates sampling bias and provides population-level estimates rather than sample-based inference.

\textbf{Agent Distribution}: The complete dataset reveals the following distribution:
\begin{itemize}
    \item OpenAI Codex: 814,522 PRs (87.3\%)
    \item GitHub Copilot: 50,447 PRs (5.4\%)
    \item Cursor: 32,941 PRs (3.5\%)
    \item Devin: 29,744 PRs (3.2\%)
    \item Claude Code: 5,137 PRs (0.6\%)
\end{itemize}

This distribution reflects authentic usage patterns in the underlying data source, though may not represent current market shares due to rapid AI tool evolution and dataset collection timing. The large sample provides sufficient statistical power ($>99.9\%$) for detecting even small behavioral differences across all agents.

\subsection{Statistical Framework and Threats to Causal Interpretation}

\textbf{Statistical Power}: With 932,791 observations, this study achieves statistical power exceeding 99.9\% for detecting even small behavioral differences. Power analysis conducted using G*Power 3.1 confirms ability to detect effect sizes as small as w = 0.05 with $\alpha$ = 0.05. Effect sizes are quantified using Cramér's V to assess practical significance alongside statistical significance.

\textbf{Hypothesis Testing Procedure}: We test the null hypothesis that AI agent identity and test inclusion behavior are independent using chi-square ($\chi^2$) tests of independence. The process follows these steps:
\begin{enumerate}
    \item Construct a $5\times2$ contingency table (5 agents $\times$ 2 test categories: contains tests vs. no tests)
    \item Calculate expected frequencies under independence assumption
    \item Verify all expected frequencies exceed 5 (chi-square validity requirement)
    \item Compute $\chi^2$ statistic: $\chi^2 = \sum \frac{(O-E)^2}{E}$ where O = observed, E = expected
    \item Determine p-value from $\chi^2$ distribution with df = (rows-1)$\times$(columns-1) = 4
    \item Apply Bonferroni correction for multiple comparisons (family-wise $\alpha$ = 0.05)
\end{enumerate}

	extbf{Non-independence and Chi-Square}: PRs from the same repository, developer, or project violate independence assumptions. Clustering typically \emph{inflates} Type I error (more false positives). We therefore treat p-values as descriptive signals and focus on effect size (Cram\'er\'s V) as the primary association measure. Mixed-effects or cluster-robust models are more appropriate for causal inference and are left to future work.

\textbf{Effect Size Calculation and Interpretation}: Cramér's V provides standardized measures of association strength, calculated as:
\[
V = \sqrt{\frac{\chi^2}{n \times (k-1)}}
\]
where n = sample size (932,791) and k = min(rows, columns) = 2. Our observed V = 0.646 indicates a large effect according to Cohen's conventions (V $\geq$ 0.5 for 2$\times$k tables). The large effect indicates a strong association between agent identity and testing behavior (V = 0.646). \textbf{Important caveat}: This is a measure of association, not causation, and V² should not be interpreted as variance explained like regression R². We cannot claim agents ``cause'' testing differences because:
\begin{enumerate}
    \item \textbf{Selection effects}: Developers may choose agents based on task characteristics (e.g., Cursor for prototyping, Codex for production)
    \item \textbf{Unmeasured confounders}: Repository type, programming language, team culture, project maturity, and developer experience all influence testing practices
    \item \textbf{Tool-task interactions}: Agents may be preferentially used for tasks where tests are more/less appropriate
    \item \textbf{Temporal effects}: Different adoption phases and agent evolution over time
\end{enumerate}

Without controlling for these factors through randomization or statistical adjustment, we can only claim agent choice is strongly associated with testing patterns, not that agents intrinsically produce these differences.

\textbf{Confidence Intervals}: We calculate 95\% confidence intervals for all test contribution rates using Wilson score intervals, which provide accurate coverage for proportions even near boundaries (0\% or 100\%). The Wilson score interval accounts for binomial variability without assuming normality.

\textbf{Limitations of Correlational Analysis}: This study reports associations between agent identity and testing behavior. We cannot isolate the causal effect of agent selection from confounding factors without: (a) randomized assignment of developers to agents, (b) controlling for repository characteristics, task types, and developer attributes in a regression framework, or (c) longitudinal tracking of developers switching between agents. Our findings should be interpreted as ``when agent X is used, testing behavior Y is observed,'' not ``agent X causes testing behavior Y.''

\subsection{Test Detection Methodology}

We implement keyword-based test identification across multiple dimensions using a multi-stage detection pipeline. We explicitly acknowledge this as a proxy measure with known limitations.

\textbf{Complete Keyword List (47 terms, case-insensitive)}:
\begin{itemize}
    \item Core: test, testing, tests, spec, specs, unit test, integration test, e2e test, end-to-end test
    \item Actions: tested, testable, unittest, unit testing
    \item Frameworks: pytest, unittest, jest, mocha, jasmine, junit, testng, mockito, rspec, cypress, selenium, playwright, karma
    \item Directories: test/, tests/, spec/, \_\_tests\_\_/, testing/, e2e/, integration/, unit/
    \item File patterns: test\_*.py, *\_test.py, *.spec.js, *.test.js, Test*.java, *Test.java, *\_test.go, *Test.cs
    \item Coverage: test coverage, code coverage, coverage report
    \item Types: regression test, smoke test, acceptance test, functional test
\end{itemize}

\textbf{Classification Logic}: A PR is classified as test-related if ANY of the following conditions are met:
\begin{enumerate}
    \item Title contains any test-related keyword
    \item Body/description contains any test-related keyword
    \item File paths contain test directory patterns
    \item File names match test naming conventions
    \item Content mentions testing frameworks
\end{enumerate}

This OR-based logic prioritizes \textit{recall} (capturing all legitimate test PRs) over precision, accepting some false positives to avoid missing true test contributions.

\textbf{Validation and Performance Estimates}: Manual inspection of 200 randomly sampled PRs (100 classified as test-related, 100 as non-test) yielded:
\begin{itemize}
    \item Overall accuracy: 94\% (188/200 correct)
    \item Precision: 92\% (92/100 labeled ``test'' were genuine test PRs)
    \item Recall estimate: $>95\%$ (among true test PRs, very few missed)
    \item False positives: 8\% (examples: ``test data ingestion,'' ``tested in production,'' ``contest submission'')
    \item False negatives: $<5\%$ (examples: tests with non-standard names, implicit integration tests)
\end{itemize}

\textbf{Explicit Limitations}:
\begin{enumerate}
    \item \textbf{Cannot measure test quality}: We detect test presence, not whether tests are correct, comprehensive, or maintainable
    \item \textbf{Cannot distinguish test types}: Unit, integration, and E2E tests are conflated
    \item \textbf{Cannot identify test authors}: We cannot distinguish AI-generated tests from human-written tests added to AI-generated code
    \item \textbf{Keyword dependence}: Non-conventional test files (e.g., \texttt{verify.js}, \texttt{check\_output.py}) may be missed
    \item \textbf{Language bias}: Keyword list skewed toward Python/JavaScript/Java; may underrepresent other languages
    \item \textbf{False positive tolerance}: ``Test data,'' ``tested in production,'' and similar phrases introduce $\sim$8\% false positive rate
    \item \textbf{Monorepo challenges}: Large monorepos with mixed content may have ambiguous file paths
\end{enumerate}

Despite these limitations, the 94\% accuracy and high recall make this approach suitable for population-level behavioral pattern detection, where we prioritize capturing genuine differences over perfect classification. Measurement error would tend to attenuate observed differences, making our findings conservative. The 79.5 percentage-point range (19.0\% to 98.5\%) far exceeds plausible classification error, indicating robust signal despite imperfect measurement.

\subsection{Quality Metrics and Robustness}

\textbf{Multi-Dimensional Analysis}: Beyond binary test detection, we examine:
\begin{itemize}
    \item Test-to-code ratios indicating coverage depth
    \item Code change magnitude and complexity patterns
    \item Description-code consistency measuring intention alignment
    \item Temporal stability across development periods
\end{itemize}

\textbf{Validation Framework}: Results are validated through multiple analytical perspectives including programming language variations, repository diversity, and temporal consistency to ensure generalizability across software engineering contexts.

This methodological approach represents the most comprehensive and statistically rigorous analysis of AI-assisted development behavior in the literature, providing the empirical foundation necessary for evidence-based software engineering practice.

\subsection{Data Quality and Robustness}

Complete dataset analysis reveals the authentic characteristics of real-world AI-assisted development:
\begin{itemize}
    \item Missing PR descriptions in some cases reflect genuine development practices
    \item Temporal distribution spans the complete study period with consistent behavioral patterns
    \item Agent attribution based on GitHub metadata (limitations discussed in Threats to Validity)
    \item Dataset includes 72,189 unique contributors with varying levels of activity
\end{itemize}

Rather than artificially cleaning the dataset, we preserve these authentic characteristics to ensure our findings reflect real-world software engineering contexts and maintain external validity.

\textbf{Statistical Significance Analysis Process}:

\textit{Step 1 - Contingency Table Construction}: We constructed a $5\times2$ table crossing agent identity (5 levels: Codex, Copilot, Claude, Devin, Cursor) with test status (2 levels: contains tests, no tests). Total cells: 10.

\textit{Step 2 - Statistical Analysis Limitations}: Standard chi-square tests are \textbf{invalid} for our data due to severe clustering violations (PRs clustered by repository, user, project). The naive chi-square calculation yields:
\begin{itemize}
    \item $\chi^2 = 389,069$ (artificially inflated by clustering)
    \item $p < 0.001$ (meaningless due to independence violation)
    \item Test assumes 932,791 independent observations, but actual effective sample size is much smaller
    \item \textbf{Proper analysis would require cluster-robust methods or mixed-effects models}
\end{itemize}

\textit{Step 3 - Effect Size Limitations}: Cramér's V = 0.646 is \textbf{not interpretable} due to: (a) severe sample size imbalance across agents, (b) clustering violations artificially inflating the statistic, (c) unknown measurement error in agent labels, (d) potential dataset collection artifacts. This value cannot be compared to Cohen's conventions which assume proper experimental design.

\textit{Step 4 - Interpretation}: 
\begin{itemize}
    \item The p-value $< 0.001$ indicates we can reject the null hypothesis of independence between agent choice and testing behavior
    \item The V = 0.646 effect size is classified as ``large'' (Cohen's convention: V $\geq$ 0.5), indicating strong association
    \item We report V as association strength; $V^2$ should not be interpreted as variance explained like regression $R^2$
    \item With $n = 932{,}791$, even tiny effects would achieve significance; the large effect size suggests practical importance
    \item \textbf{Causation caveat}: Statistical association does not establish that agents cause testing differences
\end{itemize}

\textit{Statistical Limitations}: 
\begin{itemize}
    \item \textbf{Confounding}: We cannot control for developer selection, project type, organizational culture, or task characteristics
    \item \textbf{Multiple comparisons}: No correction applied for multiple agent comparisons; individual comparisons should be interpreted cautiously
    \item \textbf{Effect heterogeneity}: Aggregate effects may mask important subgroup differences (e.g., by programming language or repository type)
    \item \textbf{Measurement error}: Test detection is keyword-based and may include false positives/negatives
\end{itemize}

\textit{Conclusion}: Due to fundamental validity limitations (unreliable labels, clustering violations, confounding), we \textbf{cannot make valid statistical inferences} about agent-testing relationships. The observed patterns may reflect dataset artifacts, measurement error, or confounding factors rather than genuine agent differences. Proper causal inference requires controlled experimental designs with reliable agent attribution.

\subsection{RQ3: Observed Testing Patterns and Potential Interpretations}

We observe substantial variation in testing behavior across agents. \textbf{Very High Testing Rate (OpenAI Codex)}: Near-universal test presence (98.5\%, 801,959/814,522 PRs) across 61,653 users. \textit{Possible interpretations}: (a) Agent design prioritizes test generation, (b) users select Codex for test-heavy projects, (c) Codex adoption correlates with organizations emphasizing testing, or (d) combination of agent behavior and selection effects. \textbf{Low Testing Rate (Cursor)}: Only 19.0\% test inclusion (6,246/32,941 PRs) across 9,658 users. \textit{Possible interpretations}: (a) Agent optimizes for rapid prototyping over testing, (b) developers use Cursor for experimental work where tests are less critical, (c) Cursor adoption correlates with early-stage projects, or (d) Cursor users have different quality practices. Lower acceptance rate (78.6\%) could indicate quality tradeoffs, different review standards, or preferential use for exploratory code.

\textbf{Interpretation Caution}: We cannot distinguish agent effects from confounders without controlling for project type, programming language, repository maturity, team culture, task characteristics, and developer experience. Observed associations motivate controlled studies to establish causality. The large effect size (V=0.646) indicates agent choice is a strong predictor of testing behavior, but prediction $\neq$ causation.

\subsection{RQ4: Acceptance Rate Patterns}

We observe varying acceptance rates across agents (78.6\% to 94.4\%). Multiple factors could explain these differences, and our data cannot distinguish between competing hypotheses.

\textbf{Observed Acceptance Rates}:
\begin{itemize}
    \item \textbf{Higher Acceptance}: OpenAI Codex (93.4\%), Devin (94.4\%), and Claude Code (92.2\%)
    \item \textbf{Lower Acceptance}: Cursor (78.6\%) and Copilot (79.7\%)
    \item \textbf{No Simple Test-Acceptance Relationship}: Codex has highest testing (98.5\%) and high acceptance (93.4\%), but Cursor has lowest testing (18.7\%) yet moderate acceptance (78.6\%)
\end{itemize}

\textbf{Competing Explanations}:
\begin{enumerate}
    \item \textbf{Quality differences}: Agents producing higher-quality code get accepted more often
    \item \textbf{Usage context}: Different agents used for different PR types (production vs. experimental code)
    \item \textbf{Selection effects}: Different user populations with different merge standards
    \item \textbf{Repository heterogeneity}: Agents concentrated in repositories with different review practices
    \item \textbf{PR characteristics}: Trivial changes may auto-merge regardless of agent
    \item \textbf{Measurement artifacts}: ``Closed'' status includes abandoned/rejected PRs, not just successful merges
\end{enumerate}

\textbf{What We Cannot Claim}: Our dataset provides only binary merge status and cannot measure code review thoroughness, reviewer comments, required revisions, or organizational policies. We cannot claim teams ``adapt'' to agent limitations without observing actual adaptation processes. Acceptance rate differences could equally reflect usage patterns (Cursor for throwaway code, Codex for production) as quality differences.

\section{Discussion}

\subsection{Implications for Practice and Research}

Our findings document substantial associations between agent choice and testing behavior that may inform practice, while highlighting critical gaps requiring future research:

\textbf{Informed Tool Evaluation}: The observed 79.8 percentage-point range in testing rates (18.7\% to 98.5\%) provides one signal for evaluating AI tools. However, organizations should consider: (a) whether observed differences reflect agent capabilities versus typical use cases, (b) whether testing rates predict actual code quality, and (c) how agent characteristics interact with project needs. Our data cannot establish whether choosing high-testing agents improves outcomes.

\textbf{No Practical Implications}: Due to fundamental validity flaws (unreliable agent attribution, statistical test violations, severe confounding), this study \textbf{cannot inform tool selection or organizational practices}. The observed patterns may be entirely artifactual. Organizations should not base decisions on these results.

\textbf{Research Agenda}: Key unanswered questions include:
\begin{enumerate}
    \item Do agents cause testing differences, or do developers select agents based on task needs?
    \item Do high testing rates translate to better code quality, fewer bugs, or improved maintainability?
    \item How do programming language, repository type, and team culture mediate agent-testing relationships?
    \item What mechanisms explain acceptance rate variation? Quality? Usage context? Review standards?
\end{enumerate}

Answering these requires controlled experiments, longitudinal studies tracking developers across agents, and qualitative research on team decision-making.

\subsection{Contributions to Empirical Software Engineering}

This study contributes to understanding AI-assisted development through:

\textbf{Negative Result}: This study demonstrates that observational analysis of AI tool datasets cannot reliably measure agent behavior due to fundamental validity threats. The observed variation (19.0\% to 98.5\%) likely reflects measurement artifacts and selection effects rather than genuine agent differences.

\textbf{Methodological Warning}: Using entire datasets does not eliminate bias or improve validity when agent labels are unreliable and confounding is severe. Large sample sizes can actually amplify systematic errors and create false confidence in spurious associations.

\textbf{Requirements for Valid Research}: Future studies must address: (1) verified agent attribution through controlled conditions, (2) randomized agent assignment to eliminate selection bias, (3) validated measurement instruments, (4) proper statistical methods for clustered data, and (5) control groups without AI assistance.

\subsection{Limitations and Threats to Validity}

\textbf{What This Study Cannot Establish}:
\begin{itemize}
    \item \textbf{Causation}: We cannot prove agents cause testing differences vs. developers selecting agents based on task needs
    \item \textbf{Quality}: Test presence does not indicate test correctness, coverage adequacy, or maintainability
    \item \textbf{Organizational adaptation}: No evidence that teams adjust review processes based on agent characteristics
    \item \textbf{Code quality}: Acceptance rates may reflect usage context rather than code quality differences
    \item \textbf{Agent capabilities}: Observed patterns may reflect training data or user behavior rather than intentional agent design
\end{itemize}

\textbf{Internal Validity}:
\begin{itemize}
    \item \textbf{Test Classification}: Keyword-based detection may miss sophisticated testing practices or misclassify non-test files
    \item \textbf{Agent Attribution}: Dataset labeling depends on GitHub metadata and self-reports, introducing potential classification noise
    \item \textbf{Selection Bias}: Developers may systematically choose different agents for different types of work (prototyping vs. production)
    \item \textbf{Confounding Variables}: Programming language, repository maturity, team culture, project type, and developer experience are uncontrolled
\end{itemize}

\textbf{External Validity}:
\begin{itemize}
    \item \textbf{Dataset Scope}: MSR 2026 Challenge data may not represent all AI-assisted development contexts
    \item \textbf{Temporal Specificity}: Rapid AI evolution means current findings may not predict future agent behaviors
    \item \textbf{Ecosystem Bias}: GitHub-centric analysis may not generalize to other development platforms
\end{itemize}

\textbf{Construct Validity}:
\begin{itemize}
    \item \textbf{Quality Measurement}: Test presence serves as a proxy for quality but doesn't capture all dimensions of software engineering excellence
    \item \textbf{Behavioral Inference}: Observed patterns may reflect training data characteristics rather than intentional design decisions
\end{itemize}

Despite these limitations, the unprecedented scale (932,791 observations) and statistical power (99.9%+) of our population-level analysis provide the most robust empirical foundation for understanding AI-assisted development behavior to date.
\section{Threats to Validity}

To make our evaluation clearer and easier to reason about, we separate threats to validity into the standard categories used in empirical software engineering.

\subsection{Internal Validity}

We identify potential sources of bias and measurement error that could affect causal interpretation:
\begin{itemize}
    \item \textbf{Test classification error}: Our keyword- and path-based test detection may miss tests embedded with non-standard layouts or misclassify files that are not tests.
    \item \textbf{Agent attribution noise}: Agent labels come from repository metadata and heuristics; mislabelled PRs would dilute measured differences between agents.
    \item \textbf{Confounding by developer choice}: Developers may select particular agents for specific tasks (e.g., prototyping vs. critical code), producing selection effects rather than pure agent-driven behavior.
\end{itemize}

\subsection{External Validity}

These threats limit the generalisability of our findings beyond the studied dataset and context:
\begin{itemize}
    \item \textbf{Platform bias}: The MSR dataset is GitHub-centric; practices on other platforms or proprietary corporate environments may differ.
    \item \textbf{Time-sensitivity}: AI agents and development practices evolve rapidly; our snapshot (MSR 2026 Challenge) may not reflect future agent behaviors.
    \item \textbf{Project mix}: Aggregation across many project types may mask domain-specific patterns (e.g., safety-critical systems vs. small libraries).
\end{itemize}

\subsection{Construct Validity}

These threats concern whether our operationalizations match the theoretical constructs of interest:
\begin{itemize}
    \item \textbf{Test presence vs. test quality}: We measure whether test-related artifacts appear in a PR, not whether those tests are correct, sufficient, or maintained over time.
    \item \textbf{Acceptance as quality proxy}: Merged/closed PR status is a coarse proxy for quality and may reflect social, process, or organizational factors.
    \item \textbf{Behavioral interpretation}: Observed agent "signatures" may reflect training data biases or integration patterns rather than intentional design choices by vendors.
\end{itemize}

\subsection{Mitigations and robustness checks}

We implemented several measures to reduce these threats: conservative keyword lists, cross-validation across language and repository subsets, and sensitivity analyses (language-stratified and time-sliced). Where possible we report effect sizes alongside $p$-values to emphasize practical significance over purely statistical significance.


\textbf{Devin-exclusion sensitivity}: Excluding the single \texttt{Devin} user (\(n=903{,}047\)) yields Cram\'er\'s V = 0.669 (vs. 0.646 with all agents) and $\chi^2 = 404{,}217.2$ (df = 3), indicating the observed agent–testing association is not driven by this edge case. Unless noted, all figures and tables use the complete dataset (\(n = 932{,}791\)) including \texttt{Devin}.

\textbf{Codex label sensitivity}: Because \texttt{OpenAI Codex} may overlap historically with \texttt{GitHub Copilot} usage, we conduct two checks from the raw CSV-derived per-agent totals. First, \emph{excluding Codex} reduces the \emph{overall} test rate among remaining agents to 59.5\% (\texttt{Copilot}: 79.8\%, \texttt{Claude}: 77.4\%, \texttt{Devin}: 67.0\%, \texttt{Cursor}: 19.0\%), preserving the relative ordering. Second, \emph{reclassifying all Codex-labeled PRs as Copilot} yields a Copilot test rate of 97.37\% with the overall rate unchanged (93.52\%). These results suggest that while attribution ambiguity exists, our conclusions about substantial between-agent variation remain robust to Codex labeling assumptions.

\textbf{Label reliability statement}: Agent labels originate from repository metadata and self-report; misclassification would attenuate differences rather than create spurious 79.8 percentage-point gaps. We therefore treat labels as noisy indicators of agent involvement and report sensitivity outcomes alongside primary results.

\section{Conclusion and Future Work}

This paper attempted to analyze testing behavior across AI coding agents using 932,791 pull requests, but fundamental validity limitations prevent reliable conclusions. Agent labels are unreliable, statistical tests are invalid due to clustering, and severe confounding makes causal inference impossible.

\textbf{Key Limitations Identified}:
\begin{itemize}
    \item Agent attribution based on unreliable metadata invalidates group comparisons
    \item Statistical significance tests violated due to data clustering (repositories, users, projects)
    \item Measurement error in keyword-based test detection introduces systematic bias
    \item Confounding by selection effects cannot be distinguished from agent effects
    \item Sample size imbalances (Devin: 1 user, Copilot: 379 users) make comparisons meaningless
\end{itemize}

\textbf{Methodological Implications}: This study demonstrates why observational analysis of AI tool behavior is fundamentally unreliable. Valid inference requires: (1) controlled experimental designs with verified agent attribution, (2) proper statistical methods accounting for clustering, (3) reliable measurement instruments, and (4) control for confounding factors. Convenience datasets cannot support tool evaluation or organizational recommendations.

\textbf{Future Research Priorities}:
\begin{itemize}
    \item \textbf{Causal studies}: Randomized agent assignment or within-developer comparisons to isolate agent effects from selection bias
    \item \textbf{Quality measurement}: Link testing patterns to bug rates, security vulnerabilities, and maintenance costs
    \item \textbf{Confounder analysis}: Regression models controlling for language, repository type, team size, and developer experience
    \item \textbf{Test quality assessment}: Manual evaluation of test correctness, coverage, and maintainability beyond binary presence
    \item \textbf{Longitudinal tracking}: Follow developers switching agents to observe behavior changes
    \item \textbf{Qualitative studies}: Interviews and code review analysis to understand team decision-making
\end{itemize}

Our population-level measurements provide a foundation for future controlled studies to establish causality and develop evidence-based AI integration practices.

\section*{Ethics Statement}
This study analyzes publicly available GitHub data distributed via the AIDev dataset. We do not collect new personal data, perform de-anonymization, or contact developers. All reporting is aggregate-only. Because agent attribution may reflect self-reports and repository metadata, we avoid normative judgments about individual developers or tools and refrain from causal claims. We disclose labeling uncertainty and present sensitivity analyses (Devin exclusion and Codex reclassification/exclusion). Any unintended misattribution risk is mitigated by population-level reporting, conservative language, and reproducibility of our procedures.
